## 概述
本质：**快但小的存储放热数据，慢但大的存储放冷数据，中间用一套机制来做换入换出**

| 计算机概念     | Agent 记忆对应    |
| --------- | ------------- |
| CPU 寄存器   | 当前 token 的注意力 |
| L1/L2 缓存  | 上下文窗口（工作记忆）   |
| RAM       | 会话内的对话历史      |
| 硬盘/SSD    | 长期记忆（文件/数据库）  |
| 虚拟内存/Swap | RAG 检索        |

**核心只存那些只存在于对话汇总，无法从其他地方获取的信息**。能从文档、代码、git里推导的都不存

Claude Code的四种记忆类型：**user（用户画像）、feedback（行为反馈）、project（项目动态）、reference（外部资源)**
- 用户说“我是做后端的，前端不熟”
- 用户纠正了一个行为，“不要在commit信息里加emoji”
- 团队决定“下周三之前不要合并PR，要切release”
- 同事说“bug都在Other项目里”


## 文件派
Claude Code用**纯文本文件**

### 双层架构
索引+正文的双层结构

#### 第一层 MEMORY.md 索引文件
放在 `~/.claude/projects/<项目路径>/memory/` 目录下
它的角色是**目录页**，每一行是一条指针，指向一个具体的记忆文件
```md
- [用户偏好](user_preferences.md) — 后端出身，前端不熟，偏好简洁代码
- [项目规范](project_conventions.md) — pnpm，vitest，commit 用中文
- [部署拉闸](deploy_freeze.md) — 2026-04-15 前不合并非关键 PR
```
MEMORY.md在每次会话开始的时候会被加载到system prompt里，所以必须内容精简

#### 第二层 独立记忆文件
每个记忆是独立的.md文件，带YAML frontmatter
description用于精选注入时，判断这条记忆和当前任务是否有关系
```md
---
name: 项目规范
description: 包管理器、测试框架、commit 规范等项目约定
type: feedback
---

用 pnpm 不要用 npm。
**Why:** 用户明确要求，团队统一规范。
**How to apply:** 所有 install/add 命令用 pnpm。

测试用 vitest 不要用 jest。
**Why:** 项目已配好 vitest，jest 会引入额外依赖。
```

### 暴力约束
MEMORY.md 有一个硬限制：**200 行 或 25KB，谁先到谁算数，**超了就截断，末尾追加一条警告
物理上限倒逼 Agent 只保留最重要的记忆


### 记忆读写
**记忆的读写完全靠 Agent 自己，用现有的 Write/Edit 工具**，所以**记忆的质量完全取决于 prompt 设计，而不是代码逻辑**

Claude Code 在 system prompt 里详细规定了什么该存、什么不该存、格式怎么写、怎么避免重复。Agent 按这些指令操作文件，如果记忆质量不好，调 prompt 就行，不需要改代码


### 精选注入
会话开始时不会全部加载独立的记忆文件，**用 Sonnet 做 relevance selection，完全不阻塞主流程**

核心流程：
1. 用户输入一条消息
2. 系统**立刻**提取用户的 prompt，异步发给 Sonnet，不等结果
3. 主模型**同时开始正常工作**，不需要等 Sonnet 返回
4. Sonnet 在后台拿所有记忆文件的 frontmatter（文件名 + description + type），跟用户 prompt 做匹配
5. Agent Loop 每一轮迭代时**轮询一下**：Sonnet 返回了吗？返回了就消费结果，没返回就跳过，下一轮再看
6. 当 Sonnet 结果到达时，挑出的记忆文件作为附件注入当前轮次的消息中

超过 1 天的记忆还会附带一条提示（"这条记忆是 X 天前的，记忆是时间点快照，不是实时状态"），提醒模型别盲目相信旧信息


### 自动提取
Claude Code有一个自动提取机制，每次 query 结束后（模型的最终响应不再有工具调用时），系统会 fork 一个后台 Agent，去分析最近几轮对话，提取值得记住的信息

后台agent行为存在严格限制：
- **只有 5 轮** 工具调用预算（防止跑偏）
- **只能读不能写代码**（Read/Grep/Glob 可以，但只对记忆目录有 Edit/Write 权限）
- **跟主 Agent 互斥**：如果主 Agent 这一轮已经手动写了记忆，自动提取就跳过，避免重复
- 失败了不会阻塞用户：后台跑的，静默失败，下一轮重试

## 数据库派
OpenClaw使用**SQLite + sqlite-vec + FTS5，三位一体**


### 存储架构
OpenClaw 用 SQLite 数据库存储记忆，路径在 `~/.cache/openclaw/agents/memory/<agentId>.sqlite`

有三张核心表：
- **chunks 表**：存记忆文本和元数据（id、路径、来源、行号范围、hash、embedding）
- **chunks_vec 表**：sqlite-vec 虚拟表，存向量索引，支持余弦距离搜索
- **chunks_fts 表**：FTS5（SQLite 内置的全文搜索引擎）虚拟表，支持 BM25 排序，给记忆文本建了一个"搜索引擎"

一条记忆同时被三种方式索引：原文、向量、关键词

### 混合检索
核心设计：向量70%+关键词30%
1. **向量路径**：把查询文本转成 embedding，在 chunks_vec 表里做余弦距离搜索
2. **关键词路径**：用 FTS5 的 BM25 排序做全文检索
3. **合并**：两路结果去重后，按 `0.7 × 向量分 + 0.3 × 关键词分` 加权合并

### 时间衰减
指数衰减机制，一条记忆在 N 天后，权重降为原来的一半
但**MEMORY.md 等常驻文件豁免衰减**
```
衰减系数 = e^(-λ × 天数)
λ = ln(2) / 半衰期天数
```
大部分新的信息通常比旧的更有用，但也有例外情况（如：核心技术栈的选型一直没变过），所以是可选开启

### Memory Flush
压缩之前先存档：让 Agent 把当前会话中值得长期保存的信息写入记忆文件，然后再做压缩

触发条件：
- **软阈值**：当已用 token 达到 `上下文窗口 - 20000 - 4000` 时触发。20000 是给模型输出预留的空间（`reserveTokensFloor`），确保压缩后模型还有足够的 token 来生成回复；4000 是 flush 的提前量，在压缩真正触发前先把重要信息存档
- **强制阈值**：当 transcript 文件（存对话记录的文件）大小超过 2MB 时无条件触发


### Embedding
向量搜索的前提是得先把文本变成向量，OpenClaw支持OpenAI、Gemini、Voyage、Mistral 等云端方案，也可以用 Ollama 或者 node-llama-cpp 跑本地小模型


## 选型
简单粗暴的标准：
- **单人用、记忆少于 200 条，走文件派：** 这么做的好处是简单、透明、用户可以直接编辑
- **多人用、记忆超过 500 条、需要语义搜索，走数据库派：** 当记忆量大到靠文件名已经找不到东西的时候，向量搜索就变成了刚需
