## 概述
RAG（Retrieval-Augmented Generation，检索增强生成）的核心思路：**在模型生成回答之前，先去"查资料"，把相关内容塞进上下文，让模型有据可依**
🌰：公司内部的SDK文档、业务数据的PDF等

## 第一步 文档加载
RAG 的第一步是把你的文档变成可检索的文本，不同格式的处理差异较大，而**数据质量决定了 RAG 的上限**
- Markdown：最友好，本身就是纯文本，有天然的结构信息
- PDF：最头疼，同样一份 PDF，用纯文本提取很容易出现结构混乱的情况（表格乱码、多栏排版混合）；结构化提取效果好很多，但成本也高
- 代码文件：比较特殊，有函数、类、模块这些结构单元。把一个函数从中间劈开分成两个 chunk，两个 chunk 单独看都没有意义
- 网页：需要去噪，侧边栏、广告、cookie提示等这些内容占了页面内容的一大半，但对检索来说都是噪音。可以通过工具来只提取正文

## 第二步 分块
上下文窗口有限，不可能把一整份 50 页的文档塞进去，需要找到最相关的那几段塞进去

### 分块主流策略
- **固定大小分块**：按 token 数量硬切。简单粗暴，但可能把一句话从中间劈开
- **递归分块**：按段落分，段落太长了再按句子分，句子还太长了再按 token 分，尽量保留语义完整性
- **语义分块**：用 embedding 模型判断相邻段落的语义相似度，在语义变化较大的地方切开

### 分块效果测试
- 语义分块会导致切出来的chunk太碎了，每个包含的上下文信息太少，模型拿到之后没法做出准确的回答
- 递归分块在大多数场景下就是最好的选择，Chunk Size 设为 256-512 token 这个区间


### 代码文件拆分
需要使用**AST-based chunking**，用 AST（抽象语法树）解析代码，按函数、类、模块这些语义单元来切分。如果用token分，一个函数被从中间切开，两半各自都没有意义

但因为代码有明确的结构（import、类型、调用链），用确定性的工具（grep、glob）去导航比用向量搜索更准确


## 第三步 Embedding
分好块之后，需要把每个 chunk 变成一个向量（一串数字），这样才能做相似度搜索。这个过程叫 embedding

在一个巨大的多维空间，每一篇文档在这个空间里有一个位置。语义相近的文档，位置就靠近；语义不相关的，位置就远

Embedding 模型做的就是帮你算出每个 chunk 在这个空间里的坐标。查询的时候，把用户的问题也算一个坐标，然后找跟它最近的那些 chunk，即向量搜索

## 第四步 存储
embedding 算出来后，需要存到一个支持向量搜索的数据库里，但**向量数据库的选择对 RAG 系统质量的影响很小**

简单的决策路径：**本地/边缘用 sqlite-vec，原型验证用 ChromaDB，已有 Postgres 就用 pgvector，大规模生产环境直接上 Qdrant、Pinecone 或 Milvus 三者任选其一**


## 第五步 检索
需要把问题转成向量，去数据库里找最相关的 chunk

存在一个核心问题：**语义相似不等于任务相关**，embedding 模型对操作性和描述性内容的区分能力有限
🌰：用户搜"怎么部署"，向量搜索可能返回"部署架构图"（语义近）而不是"部署命令清单"（用户真正需要的）


## 索引更新
文档不是一成不变的，当文档发生更新时，索引需要跟着更新

两种策略：
- 全量重建：成本较高，适合文档量不大或者变更量超过 10-15% 的场景
- 增量更新：只处理变更的部分，用 hash 比对文件内容是否变化。效率高，但实现复杂一些

OpenClaw的做法：增量更新用 hash 检测变化，但全量重建的时候用**临时数据库 + 原子交换**的方式，先在一个临时 SQLite 文件里建好新索引，确认没问题后一次性替换旧的

**embedding 模型升级的场景**：新模型生成的向量和旧模型的不在同一个空间里，不能混用，必须做全量重建。
