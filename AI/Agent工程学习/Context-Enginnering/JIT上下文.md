## 概述
**JIT（Just-In-Time）**：用的时候才去拿，不提前塞内容，等 Agent 真正需要某段信息时再按需加载

## 路线一 Agentic Search
Agent 自己决定下一步该搜什么、该读什么，运行时用工具主动探索
1. Glob：按文件名搜索，只返回路径
2. Grep：按内容搜索，只返回命中的行
3. Read：按需读取完整内容

选型原因：
- 精确度：Grep 找的是精确匹配，而embedding 检索是模糊的，可能给你"语义相关但不是那个函数"的代码
- 实时性：正在改代码，文件分分钟在变，Grep 永远搜的是当前文件。而RAG的索引是预计算的，改了一行代码索引就过期了
- 可观测：Agent执行的每一步都是可见的，搜了什么、搜到了什么、读了哪个文件
- 零额外基础设施：不需要向量数据库、不需要预计算 embedding、不需要索引更新机制，只需要文件系统

Claude Code的工具调用优化措施：
- **Prompt Cache**：System Prompt和历史的对话内容都不变，只有新增的工具调用结果在末尾
- **Explore 子 Agent**：如果涉及大范围的搜索，会用子agent在独立的上下文窗口里搜索，不污染主agent的上下文

## 路线二 RAG
关键区别在于：**内容有没有确定性的结构可以遍历**。代码有 import 关系、类型定义、目录结构，所以确定性工具（grep、find）比概率性检索（embedding）更准。但知识库通常没有这种可遍历结构，语义检索反而是更自然的"按需加载"方式

按需发生在更早阶段，需要预先建好 embedding 索引，查询时一次检索拿到 top-k 结果

主要适用场景：
- **文档问答**：用户问"我们的退款政策是什么"，知道答案一定在某几份文档里，预先检索比 Agent 自己翻快得多
- **非结构化内容**：一大堆PDF报告，会议纪要等，没有好的目录结构让 Agent 去"探索"
- **延迟敏感**：RAG 一次检索就出结果，比 Agent 自己搜三四轮快


## 路线三 Context Offloading
[Manus的JIT思路](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)：不光"按需读入"，还能"主动卸载"。把上下文里已经用过的信息**写出去**，需要时再读回来。

具体策略：**把旧的工具结果卸载到文件系统里，只在上下文中保留路径**，Agent 需要的时候再读。文件路径就是恢复信息的"快捷方式"，**上下文里存的是"怎么恢复信息"，而不是信息本身。**

## 路线总结
核心目标：**让模型在正确的时间看到正确的信息**

| 路线                     | 核心机制                          | 适合场景                     |
| ---------------------- | ----------------------------- | ------------------------ |
| **Agentic Search**     | Agent 用工具主动探索（Glob/Grep/Read） | 代码导航、探索性任务、内容频繁变化        |
| **RAG**                | 预建索引，查询时语义检索 top-k            | 知识库问答、非结构化文档、延迟敏感        |
| **Context Offloading** | 用过的信息卸载到文件，需要时再读回             | 长链路任务（50+ 轮工具调用）、上下文即将爆满 |
