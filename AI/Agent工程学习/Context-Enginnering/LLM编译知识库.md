## 概述
RAG的问题：
- 每次查询都是从零开始，相同的问题Agent会做三次完全相同的工作
- 跨文档的关联，RAG几乎发现不了



核心思路：让 LLM 提前把原始文档"编译"成结构化的 wiki 页面，建好交叉引用和索引，查询的时候，直接在编译产物上检索。**每次新增一篇文档，LLM 会把新信息整合进已有的知识体系里**

类比：**原始文档就是源码，LLM 就是编译器，Wiki 就是编译产物**

## 三层架构

### Layer1 raw 原始素材
收集的所有原始材料：文章、论文、PDF、截图、数据文件
这一层是只读的，LLM可以读但不能改

### Layer2 wiki 编译产物
LLM 生成和维护的结构化 Markdown 文件，它负责创建页面、更新内容、维护交叉引用、保持一致性
wiki存的是经过整合的知识：实体页面、对比分析、综述页面、时间线

### Layer3 schema 操作规范
一个配置文件告诉LLM这个wiki的结构约定、命名规范、工作流程

## 核心操作
### Ingest 摄入
新素材进来的时候，LLM会读完原始文档，创建一个摘要页面，然后扫描已有的 wiki 找到所有相关的实体和概念 => 更新它们的内容、补充新信息、标注矛盾、建立交叉引用，最后更新索引和日志

### Query 查询
在 wiki 上提问，LLM 先读 index.md 找到相关页面，再深入读具体内容，综合回答并标注来源

**好的回答可以反写回 wiki：**一个对比分析的问题，LLM 读了两边的页面，给了一个详尽的对比。这个对比分析本身就是有价值的知识，于是把它存成一个新的 wiki 页面 `xxx对比.md`，下次任何人问类似的问题，直接就能找到

**每一次探索都在给知识库增值，而不是一次性消费**

### Lint 清理

定期做一次健康检查：主动巡检、提前发现

- 有没有页面之间互相矛盾？
- 有没有被新信息推翻的旧内容？
- 有没有孤立的页面（没有任何其他页面链过来）？
- 有没有重要概念被提到了很多次，但还没有自己的专属页面？
- 有没有信息缺口可以通过搜索来补充？

## 三级缓存
**越常用的信息离上下文越近，越原始的信息离上下文越远**
### L0 system prompt
index.md常驻system prompt，是整个知识库的"目录"。每个 wiki 页面一行，包含链接和一句话摘要，可以让LLM知道知识库里有什么，但不需要把所有内容都加载进来

### L1 按需加载
用户提问的时候，LLM 通过 index.md 定位到相关页面，用 Read 工具读取。只读需要的，不读不相关的

### L2 必要回溯
如果 wiki 页面的信息不够详细，LLM 可以回到 raw/ 去读原始文档


## 编译知识库&RAG选型
- 用编译知识库的场景：个人或小团队的知识体系，文档量不大（几十到几百篇），内容相对稳定，需要知识持续积累和跨文档关联。🌰：个人研究笔记，课程知识体系
- 用RAG的场景：文档量大（几千几万篇），内容频繁变动，不可能也没必要全部"编译"。🌰：客服知识库、产品文档中心、法律法规库
