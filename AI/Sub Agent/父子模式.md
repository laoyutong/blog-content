## 概述
Sub Agent**是一种上下文管理策略：每个子 Agent 有自己独立的上下文窗口，探索完把结果压缩回传，父 Agent 的上下文始终保持干净**


## 父子模式
最基础的Multi-Agent架构，父 Agent 生一个子 Agent，给它一个任务，等它干完，拿回结果

委派任务的两种方式：
- **轻量委派**：只给子 Agent 一个任务描述，让它自己去探索。🌰："找出所有引用了 xxx 函数的文件"，子 Agent 从零开始，自己决定怎么搜、搜哪里。这种方式适合探索性任务
- **重量委派**：除了任务描述，还附带一些上下文片段，可能是一段代码、一份文件内容、或者前面对话的关键摘要。子 Agent 有了更多背景信息，不需要从零开始。这种方式适合已经知道方向、只是需要子 Agent 深入挖掘的场景

子Agent完成任务的结果回传方式
- Claude Code：子Agent的输出结果作为工具结果直接注入父Agent的上下文
- OpenClaw：**Announce Queue**机制，子Agent完成之后结果先进入通知队列，有防抖间隔+指数退避重试，防止父Agent会阻塞等待，或者被子Agent的中间状态频繁打断
- OpenCode：分阶段编排，Phase 1 最多派 3 个 Explore Agent 并行出去搜集信息，Phase 2 切回串行设计，逐步执行。先让几个人各自去调研，等调研结果都回来了，再坐下来一步步推进

## 隔离思路
需要保证**多个 Agent 同时跑的时候不互相干扰？**

### 思路一：共享内存，进程内隔离
最轻量的方案，所有 Agent 跑在同一个进程里，用语言层面的机制来隔离状态

Claude Code使用Node.js的**AsyncLocalStorage**，给每个子 Agent 创建独立的异步上下文。每个子 Agent 启动时，Claude Code 会给它克隆一份文件状态缓存，而不是共享同一份，这样一个子 Agent 改了文件状态，不会影响另一个子 Agent 看到的数据


方案的好处是**零 IPC(进程间通信) 开销**，因为都在同一个进程里，没有跨进程通信，启动快、内存压力也小。坏处是隔离不够彻底，如果有人不小心用了全局变量，还是会互相覆盖


OpenCode虽然在搜集信息阶段会并行派出多个 Explore Agent，但所有对文件的实际操作都是串行的，同一时间只有一个 Agent 在读写文件系统。牺牲了一些并行效率，但省掉了所有并发控制的复杂度

### 思路二：Worktree，文件系统完全隔离
针对子Agent需要走破坏性操作的场景，🌰：大规模重构、实验性修改等，不期望直接在主代码目录上动手，防止改坏

Claude Code用`git worktree`给子Agent创建一个单独的工作目录，改好了再merge回来，改坏了就直接删掉。为了节省磁盘空间不会重复安装`node_nodules`这类依赖目录，用symlink指回主目录的，只有源码文件是独立副本

方案的好处是**源码层面彻底隔离**，子 Agent 在 worktree 里怎么改都不影响主目录。坏处是**开销大**，创建 worktree 要时间，源码也多占一份磁盘。所以它适合那种"子 Agent 要做高风险操作"的场景，不适合日常的小任务委派

### 思路三：队列串行化
OpenClaw的Lane模型不做复杂的状态隔离，用队列来保证同一个 session 里的操作按顺序执行，天然不会冲突。

消息到达后先进 session 级别的队列（保证 session 内串行），session 队列处理时再进全局 lane 的队列（控制并发上限）。两层队列嵌套在一起，既保证了单 session 内的操作有序，又允许不同 session 之间合理并发

大部分 Agent 场景其实不需要"两个 Agent 同时改同一个文件"这种高难度的并发操作，用队列把同一个 session 的操作排好队，就能解决 90% 的并发问题

## 并发安全

### 文件冲突
多个 Agent 并行工作时，Read 操作可以随便并发，读文件不改状态，谁先谁后都无所谓。但 Edit 操作必须串行，两个 Agent 同时改同一个文件，结果就是互相覆盖

Claude Code 在工具层面做了这个区分：只读工具标记为可并发，写入工具排队执行

### 状态泄露
两个子 Agent 共享了一个模块级别的变量，一个改了另一个还在用旧值

核心原则是：**隔离是默认的，共享是可选的**。任何跨 Agent 的状态共享都必须是显式决定的，不能是意外发生的

### AbortController传播
父 Agent 取消了一个任务，子 Agent 也必须跟着停下来，不然子 Agent 还在那里消耗资源

OpenClaw 的做法是把 abort signal 沿着整个 Agent 树往下传播，父 abort 了，所有子孙都收到信号，快速释放资源

### 深度限制
防止 Agent 无限消耗资源，子 Agent 如果再派子 Agent，理论上可以无限嵌套下去

- OpenClaw 直接设了一个硬限制：`maxSpawnDepth = 1`，也就是子 Agent 不能再派子 Agent，它就是叶子节点。
- Claude Code 没有设硬限制，而是靠 token 预算自然收敛：子 Agent 分到的 token 预算有限，用完了就得收工，自然没法无限嵌套下去


## 拆Agent成本
**能用一个 Agent 搞定的事，就别拆成多个**

判断是否拆，就一条标准：**你的上下文是不是真的装不下了**。如果一个 Agent 就能在上下文窗口内完成任务，那多个 Agent 只会增加不必要的复杂度

每多一个 Agent，就多了一层通信开销（子 Agent 启动、执行、回传结果）、多了一组需要调试的交互（结果不对是父 Agent 描述不清还是子 Agent 理解偏了）、多了一个潜在的故障点（子 Agent 卡住了、超时了）
