检索优化

检索优化

2026年6月21日13分钟阅读

概述

纯向量检索存在结构性局限，Embedding 模型做的事情是把文本映射到一个高维空间。在这个空间里，语义相近的文本距离近。但”语义相近”和”对用户有用”是两码事

典型失败场景：

  • 意图模糊：用户问”Python 错误处理”，向量搜索可能返回一篇介绍 Python 异常机制的博客，也可能返回一段 try-except 的代码示例。两个在语义上都跟”Python 错误处理”相关，但用户可能只想要代码示例
  • 技术术语的歧义：embedding 模型对一些领域术语的理解不如人类。比如”migration”在数据库语境下是”迁移脚本”，但 embedding 可能也把”数据迁移服务”、“云实例迁移方案”拉得很近

混合检索

思路：向量搜索擅长理解语义，关键词搜索擅长精确匹配，两个各有所长，组合起来效果最好

关键词搜索

🌰：用户搜 ECONNREFUSED，这是一个精确的错误码。向量搜索可能把它理解成”连接被拒绝”的语义，返回一堆跟网络错误相关的文档，但用户就是要找包含这个具体错误码的那几段文字

关键词搜索（BM25）在这种场景下碾压向量搜索：它不管语义，就是找”这个词出现在哪”

但用户搜”怎么让服务更稳定”，关键词搜索就懵了，“更稳定”这个词出现的地方太少了，但向量搜索能理解这些语义上的关联

OpenClaw实现

两条检索路径并行，按权重合并final_score = 0.7 × 向量分 + 0.3 × 关键词分

  • 向量路径：sqlite-vec 做余弦距离搜索
  • 关键词路径：FTS5（SQLite 内置全文搜索引擎）做 BM25 排序

存在一个问题：两条路径返回的分数根本不是一个体系的。

🌰：向量搜索给你的分数是”厘米”，BM25 给你的分数是”斤”。一个量长度，一个量重量，没法直接把 3 厘米和 2 斤加起来说”总分 5”

OpenClaw 的处理方式是把 BM25 分数做 sigmoid 归一化，这样两边的分数都在 0-1 的范围内

如果 rank < 0: score = -rank / (1 - rank) → 映射到 [0, 1)
如果 rank ≥ 0: score = 1 / (1 + rank) → 映射到 (0, 1]

大部分文档检索场景下，语义理解比精确匹配更重要，所以比例占比是70%和30%。用户的查询通常是自然语言（“怎么做 XXX”），而不是精确关键词。但关键词那 30% 也不能丢，因为它在处理专有名词、错误码、API 名称这类精确匹配场景时不可替代

候选采样：先多捞，再精选

如果最终只需要 6 条结果，OpenClaw 的做法是先多捞 4 倍，就先检索 24 条（上限 200）

这是因为向量搜索的 top-6 和关键词搜索的 top-6 可能差异很大。如果各自只取 6 条就合并，很容易丢掉某条路径上排名靠后但合并后应该入选的结果。多取一些候选，在更大的池子里做精选，效果好很多

Query改写

**用户输入的 query 本身可能就不适合直接搜索，**可以先把用户的问题”翻译”成更适合检索的形式

HyDE

Hypothetical Document Embedding 是目前最被广泛采用的 query 改写技巧

思路：先让模型生成一个”假回答”，不管对不对，先编一个看起来像答案的东西，然后用这个假回答去做检索

🌰：用户问”上次部署出了什么问题”，HyDE 会先让模型生成：“上次部署时 Nginx 配置没有更新导致 502 错误，同时数据库连接池配置不当导致超时。”

HyDE 的原始论文发现，它能显著提升零样本检索的效果，在某些基准上甚至超过了有监督的微调模型。但多了一轮 LLM 调用，延迟会增加 43-60%

子问题分解

复杂问题经常包含多个子意图：“我们的用户增长趋势和竞品相比怎么样”，这个问题至少包含两个子查询

  1. “我们的用户增长数据”
  2. “竞品的用户增长数据”

直接搜原始问题，向量搜索大概率找不到一篇同时包含两方面信息的文档。拆成两个子查询分别搜索，再合并结果，效果会好很多

总结

这些技巧的本质都是同一件事：用户问的问题和数据库里存的答案之间，表达方式可能完全不同，Query 改写就是在中间架一座桥

Reranker

**Reranker（重排序器）**做的是对候选结果做精细排序

Bi-encoder vs Cross-encoder

embedding 模型，专业术语叫 Bi-encoder（双编码器），查询(query)和文档 chunk 各自独立过一遍模型算出一个向量，然后比距离

可以理解成两种独立的计算方式，各算各的。好处是快，文档的向量可以提前算好，查询时只算一个新向量就行。坏处是两边各算各的，匹配的精准度会打折扣

Reranker 用的是完全不同的一类模型，叫 Cross-encoder（交叉编码器），而是专门为”判断两段文本的相关性”训练的模型

Cross-encoder 把查询和文档拼在一起，让模型同时看到两段文本来打分，这样精度高很多。🌰：用户问”怎么解决 502 错误”，一篇文档标题是”Nginx 配置指南”，Bi-encoder 可能觉得关系不大，但 Cross-encoder 能读到文档里确实讲了 502 的排查步骤，就会给高分

但Cross-encoder 每一对（查询, 候选）都要跑一次完整的模型推理。如果有 10 万个 chunk，跑 10 万次显然不现实

所以业界用的是两阶段架构：

  1. 第一阶段：快速召回（Bi-encoder）：向量搜索 + 关键词搜索，毫秒级，从 10 万条里筛出 20-50 条候选
  2. 第二阶段：精准排序（Cross-encoder / Reranker）：对这 20-50 条候选重新打分，毫秒级（因为候选数量少了）

实际案例分析

qmd 是 Shopify CEO 做的一个本地 Markdown 搜索引擎：用 SQLite 存索引，用 GGUF 格式的本地小模型做 embedding 和 rerank，零 API 调用，完全离线可用

它提供了三种搜索模式，正好对应检索优化的三个层次：

  • qmd search 是最基础的：纯 BM25 关键词搜索，零 GPU 成本，4 秒就出结果。搜 ECONNREFUSED 这种精确错误码，它比什么都快。但要是搜”怎么让服务更稳定”，它就傻眼了，文档里没出现过这几个字
  • qmd vsearch 加了一层语义理解：它用本地 GGUF 小模型把文档都算成向量，搜的时候走语义匹配。这样”高可用”和”服务稳定”就能关联上了。代价是你得先跑一遍 qmd update 建索引，而且要经常去同步
  • qmd query 是火力全开：先用 BM25 关键词搜索捞一批候选，再用本地模型做 rerank 精排。这个操作的精度是最高的

对大多数场景来说，默认用 BM25（快、免费），需要语义搜索时上 vsearch，对精度要求极高时再上 query

MMR去重

检索结果的多样性：搜”怎么配置 Nginx”，混合检索搜回来 6 条结果，其中 5 条都在讲 location 指令，但用户可能还需要 upstream、ssl、gzip 这些方面的信息

MMR（Maximal Marginal Relevance，最大边际相关性） 解决的就是这个问题

每次选下一条结果的时候，不仅看它跟查询的相关度，还要看它跟已经选了的结果有多”不一样”。如果一条结果跟已选的某条高度相似，它的 MMR 分数就会被扣分。OpenClaw的λ默认是 0.7：70% 看相关性，30% 看多样性

MMR_score = λ × 相关性 - (1-λ) × 与已选结果的最大相似度

判断方式：

  • 最直觉的做法是再跑一次 embedding 算语义相似度，但那又多一轮 API 调用
  • OpenClaw 用了一个更土但更快的办法：把两段文本各自拆成词的集合，看两个集合有多少重叠。重叠越多说明越像。比如两条结果都包含”nginx”、“location”、“proxy_pass”这几个词，重叠率就很高，MMR 就会扣分。这种方法叫 Jaccard 相似度，零额外成本，在这个场景下完全够用

注：MMR 在 OpenClaw 里是默认关闭的，需要手动开启。因为大部分场景下，混合检索 + 候选采样已经能提供足够的多样性了，只有在发现结果高度重复的时候才需要开 MMR

时间衰减

如果知识库包含时间敏感的内容（比如会议记录、项目状态更新、部署日志），还有一个时间衰减的优化维度。三个月前的部署日志和昨天的部署日志，在语义上可能一模一样，但用户大概率想看昨天的

OpenClaw 用指数衰减来处理这个问题：默认半衰期 30 天，一条 30 天前的记忆，分数乘以 0.5；60 天前的，乘以 0.25。即越老越不容易被检索到

衰减系数 = e^(-λ × 天数)
其中 λ = ln(2) / 半衰期
