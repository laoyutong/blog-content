## 保险丝一、工具死循环检测
核心思路：给每次调用“打指纹”，只有同样的调用+同样的结果才认定为无进展

### 四种检测器
#### 一、通用重复检测
同一种工具+同一个参数被调用了N次，但这个检测器只告警不阻断，因为有些工具确实会被合法地重复调用
🌰：Agent处理20个文件，read_file被相同的参数调用可能只是在不同的推理步骤需要重新读取

#### 二、无进展轮询检测
针对轮询类工具的检测，不光检测参数，也会看结果是否一样
当模型误判某个任务没有完成，反复查同一个状态的时候会产生效果
🌰：Agent启动一个后台任务不停地查询服务的健康检查，如果每次的状态都一样，就是无进展的轮询

#### 三、Ping-Pong检测
用于检测两个工具交替调用，检测算法是从最近的调用往回扫，看是否存在 A→B→A→B 的交替模式；关键判断条件是：**两边的结果都没变化**
如果读文件每次内容一样、写文件每次也是一样的内容，说明 Agent 在原地打转

#### 四、全局熔断器
累计一定次数的无进展调用，则**强制停止，没有例外**
这是最后一道防线，即便前三种检测器都被关了或者都没触发，全局熔断器永远在线

### 三级响应
误杀的成本较高，把一个正在工作的Agent强行停止，比让它多跑几轮浪费的时间和金钱更多
- Warning：10次；记日志，工具继续执行
- Ctitical：20次；阻断工具，Agent收到错误
- Break：30次；全局熔断，强行停止

## 保险丝二、Token预算控制
核心逻辑：给Agent设置一个**输出Token预算**，系统会跟踪累计的输出Token数
#### 1. 在90%时注入nudge消息
当输出量达到预算的90%时，会在消息流里注入一条提醒
```
"已完成 Token 目标的 87%（26,100 / 30,000）。继续工作——不要总结。"
```
- 提前10%提醒，给模型一个缓冲区来收尾
- 明确的告诉【不要总结】能更有效地利用剩余预算，防止模型“慌张”地开始总结、收尾

#### 2. 检测递减回报
如果 Agent 已经续写了 3 次以上，而且最近两次每次只增加了不到 500 个 Token——系统判定为递减回报，直接停止
Agent 可能陷入了一种「每次只说一点点新东西」的模式：可能在反复润色同一段文字，或者在添加一些无关紧要的细节，每轮增量不到 500 Token，说明没有实质性进展了

## 保险丝三、输出截断恢复
每个模型都有一个 max_output_tokens 限制，如果模型要说的话超过了这个限制，输出会被硬截断

### 1. 提高上限
如果默认8K不够可以提高至64K，模型静默重试，用户完全无感

### 2. 注入恢复消息
如果提高上限后还不够，往消息流里注入一条指令
```
"输出 Token 限制被触发了。直接从断点继续——不要道歉，不要回顾你在做什么。如果是说到一半被截了，从那个思路接着说。把剩下的工作拆成更小的块。"
```
- 不要道歉：模型的第一反应，会浪费Token
- 不要回顾：模型会把之前的复述一遍，也浪费Token
- 从断点连续：直接接上内容
- 拆成更小的快：防止下一次又被截断

### 3.认栽
如果多次恢复都不行，就直接返回不完整的结果，并标记为输出被截断
这种情况通常是任务拆分有问题或者模型做了一些不必要的展开，人工介入比自动重试更有效


## Agent退出路径
设计原则：每种退出都要有上下文
- 停了：明确Agent已经停止工作
- 为什么：是正常完成，还是用户中断，还是发生了错误
- 能做什么：是否可以继续，是否需要调整参数

Agent退出循环的方式：
1. completed 
模型返回end_turn，认为任务做完了，最理想的退出方式
2. max_turns
Agent的设置上限，跑满了就强制停止，用于防死循环和成本控制
检查发生在工具执行完成之后、下一轮API调用前，不会出现差一步完成但被硬停的情况
3. aborted-steaming
用户在流式输出时中断，会保留已经收到的文本，标记为「被用户中断」
4. aborted_tools
和上一个类似，但是发生在工具执行阶段
但已经启动的工具可能还在后台运行，如一个正在编译的进程，系统需要等工具完成或超时后再退出
5. hook_stopped
用户可以设置自定义Hook，🌰：每次Agent执行工具前，先跑一下检查脚本，代码是否通过了lint等内容，如果脚本返回不允许，Agent就停止了
6. blocking_limit
在发送API请求之前会检查一下当前上下文的token数，如果超过了【上下文窗口 - 一定阈值】，则不发请求直接退出
如果发出去让API自己拒绝，会白等一个网络往返，还可能被计费
7. prompt_too_long
上一个只是客户端的估算，有时候会有误差，发到API才发现满了
可以做两轮恢复尝试：
- Context Collapse：轻量操作，把上下文可以折叠的部分压缩掉，比如很早前执行完的工具结果
- Reactive Compact：重量级操作，调用模型对早期的对话历史做摘要压缩
如果都尝试过还是太长才会真正退出

## 保险丝协作
保险丝不是互斥的，在Agent Loop不同阶段分别守护不同的风险
- 工具调用前：死循环检测负责
- 模型输出后：Token 预算负责
- 输出异常时：截断恢复负责
- 全局层面：max_turns + 上下文检查兜底
